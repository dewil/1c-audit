# Грабли COM-доступа к 1С

Пять граблей связки «внешний скрипт + COM-соединение с 1С 8.3». Три из них
специфичны для Windows PowerShell 5.1, две — для Python и `pywin32`.

Объединяющая черта у всех пяти одна: **они тихие**. Исключения нет, скрипт не
падает, стек не пишется — просто данные на выходе неверные. Свойство читается
как `$null`, коллекция приходит пустой, запрос отбирает не тот период, метод
возвращает мусор вместо строки. Ни одну из пяти нельзя найти чтением кода:
код выглядит правильно и делает ровно то, что написано. Каждая обнаруживалась
либо опытом (падение случалось потом, в другом месте), либо сверкой двух
независимых реализаций, дававших разные цифры на одной и той же базе.

Дальше — по каждой: симптом, причина, как проверить, как лечить.

---

## 1. PowerShell не читает свойства 1С-объектов точечной нотацией

**Симптом.** `$c.Метаданные` возвращает `$null`. Ошибки нет. Дальше `$null`
едет вниз по скрипту и падает где-то далеко от причины:

```
You cannot call a method on a null-valued expression.
+ FullyQualifiedErrorId : InvokeMethodOnNull
```

**Причина.** Не «PowerShell не бросает исключение на отсутствующем свойстве»,
а **не читает существующие**. COM-адаптер PowerShell не справляется с
реализацией `IDispatch` в 1С и молча отдаёт `$null` там, где свойство есть.

**Как проверить.** Сравнить точечную нотацию с явным вызовом:

```powershell
$c.Метаданные                                                       # -> $null
$c.GetType().InvokeMember('Метаданные','GetProperty',$null,$c,@())  # -> System.__ComObject
```

**Как лечить.** Каждое чтение свойства и каждый вызов метода — через явный
`InvokeMember`. В скриптах это обычно оформляют обёртками `Pget` / `Pset` /
`Minv`. Возвращать их к `$c.Свойство` нельзя ни в одном месте: получится
`$null`, а не ошибка.

```powershell
function Pget($obj, [string]$name) {
    $obj.GetType().InvokeMember($name, 'GetProperty', $null, $obj, @())
}
function Minv($obj, [string]$name, [object[]]$args = @()) {
    $obj.GetType().InvokeMember($name, 'InvokeMethod', $null, $obj, $args)
}
```

**Два следствия, полезных для диагностики.**

Отсутствующее имя через `InvokeMember` даёт настоящее исключение, и его видно:
`DISP_E_UNKNOWNNAME (0x80020006)`. Это единственный надёжный способ отличить
«имени нет» от «имя есть, но адаптер его не прочитал».

Методы коллекций метаданных вызываются только как `InvokeMethod`. Попытка взять
`Количество` как `GetProperty` даёт `DISP_E_MEMBERNOTFOUND (0x80020003)`.

## 2. PowerShell разворачивает COM-коллекцию на выходе из функции

**Симптом.** Функция вернула коллекцию метаданных, но у результата нет её
методов:

```
catalogs type: System.Object[]
raw EX: Method 'System.Object[].Количество' not found.
```

В отчёте это выглядит как `Catalogs: 0 | Documents: 0` на конфигурации, где
их сотни.

**Причина.** Коллекции метаданных (`Справочники`, `Документы`, `Реквизиты`, …)
перечислимы через `IEnumVARIANT`. На `return $v` конвейер PowerShell
разворачивает коллекцию: наружу выходят сотни отдельных объектов, PowerShell
собирает их в `System.Object[]`, и собственных `Количество()` / `Найти()`
у результата уже нет — есть только `.Count` массива, который считает совсем
не то же самое.

**Как проверить.** Печатать тип возврата, а не значение:

```powershell
$v = Get-Catalogs $md
$v.GetType().FullName     # System.Object[]  вместо System.__ComObject
```

**Как лечить.** Запятая перед возвращаемым значением гасит разворачивание:

```powershell
return ,$v      # запятая обязательна, это не опечатка
```

Выглядит как опечатка, поэтому рядом нужен комментарий — иначе её уберут при
первой же чистке кода.

## 3. `Where-Object` / `Select-Object` возвращают строку, завёрнутую в PSObject

Самая коварная из трёх: строка выглядит правильной по всем проверкам, кроме той
единственной, которая имеет значение.

**Симптом.** Имя, полученное из конвейера, передаётся в `Найти()`, и метод
молча возвращает `$null`. Литерал с тем же текстом находится.

```
invName is PSObject     : True        # а литерал - False
-ceq literal            : True        # строки идентичны
char codes              : совпадают полностью
Найти(invName)          -> $null
Найти([string]$invName) -> FOUND
```

**Причина.** `Where-Object` и `Select-Object` отдают строку, обёрнутую в
`PSObject`. Посимвольно она равна литералу, но при вызове через `InvokeMember`
маршалится обёртка, а не BSTR, и 1С получает не то, что вы читаете в отладке.

**Как проверить.** Проверять не содержимое строки, а её тип:

```powershell
$invName -is [System.Management.Automation.PSObject]   # True - значит обёртка
```

**Как лечить.** Разворачивать аргумент перед передачей в COM. Разворачивать
надо не на месте вызова, а внутри обёрток `Minv` / `Pset`, чтобы на грабли не
мог наступить ни один вызывающий:

```powershell
function Unwrap($x) {
    if ($null -eq $x) { return $null }
    if ($x -is [System.Management.Automation.PSObject]) { return $x.psobject.BaseObject }
    return $x
}
```

Симптом на уровне отчёта был такой: целый раздел печатался пустым, потому что
`Найти()` не находил документ, результат был `$null`, а чтение свойств `$null`
снова молчало (грабля 1).

## 4. Дата в параметре запроса сдвигается на локальный часовой пояс

**Симптом.** Отбор по периоду захватывает соседний месяц. Документы, датированные
концом месяца, попадают в предыдущий; количества в отчёте вдвое больше ожидаемых.

**Причина.** Naive `datetime` из Python при передаче в параметр COM маршалится
с локальным смещением. Замерено запросом `ВЫБРАТЬ &Д КАК Д` на машине с
часовым поясом UTC+3:

| Что передаём | Что видит 1С |
|---|---|
| naive `datetime(2025, 2, 1, 0, 0, 0)` | `2025-01-31 21:00:00` |
| naive `datetime(2025, 1, 31, 23, 59, 59)` | `2025-01-31 20:59:59` |
| `pywintypes.Time(datetime(2025, 2, 1))` | `2025-01-31 21:00:00` |
| `ДАТАВРЕМЯ(2025,2,1,0,0,0)` литералом в тексте | `2025-02-01 00:00:00` |

Минус три часа — ровно смещение пояса. `pywintypes.Time` не помогает: сдвиг
тот же.

Опасность в том, куда именно попадает сдвиг. Регламентные операции закрытия
месяца датируются последней секундой месяца (`31.01 23:59:59`), и трёх часов
хватает, чтобы перекинуть их в предыдущий месяц. В отчёте это дало **8 операций
вместо 4** за один месяц, и весь раздел закрытия месяца разъехался на месяц.

**Как проверить.** Прогнать тривиальный запрос и напечатать, что вернулось:

```python
q = conn.NewObject("Запрос")
q.Текст = "ВЫБРАТЬ &Д КАК Д"
q.УстановитьПараметр("Д", datetime(2025, 2, 1))
print(q.Выполнить().Выгрузить().Получить(0).Д)
```

**Как лечить.** Не передавать даты параметрами вообще. Два рабочих способа:

```python
# 1. Месяц - целыми числами, дат нет вовсе
"ГДЕ ГОД(Дата) = &Г И МЕСЯЦ(Дата) = &М"      # Г=2025, М=1

# 2. Где дата нужна как дата - литерал ДАТАВРЕМЯ прямо в тексте запроса
def dv(d):
    return f"ДАТАВРЕМЯ({d.year},{d.month},{d.day},{d.hour},{d.minute},{d.second})"

f"ИЗ РегистрБухгалтерии.Хозрасчетный.Остатки({dv(end)}, , , )"
```

Обнаружено только сверкой с независимой реализацией на другом языке. Одна
версия — не проверка.

## 5. Имя метода — не то, что кажется, и широкий `except` это скрывает

**Симптом.** Метод «работает», но возвращает `<COMObject <unknown>>` или строку
вида `str(объект)`. Дальше сравнение с этим значением всегда даёт `False`,
и проверка, построенная на сравнении, тихо перестаёт находить что-либо.

**Причина.** Двойная. Во-первых, имени метода не существует. Во-вторых, широкий
`except Exception` ловит `AttributeError` от несуществующего имени и подменяет
результат заглушкой — так провал превращается в правдоподобный мусор.

**Как проверить.** Спрашивать у самого объекта через `GetIDsOfNames`, а не
пробовать вызвать:

```python
def has_name(obj, name):
    try:
        return obj._oleobj_.GetIDsOfNames(name)
    except Exception:
        return None

# Фактические результаты по глобальному контексту COM-соединения:
#   Строка                -> НЕТ ТАКОГО ИМЕНИ
#   String                -> dispid 200002
#   НовыйОбъект           -> НЕТ ТАКОГО ИМЕНИ
#   NewObject             -> dispid 200001
#   ЗаполнениеПроверять   -> НЕТ; у реквизита метаданных имя ПроверкаЗаполнения
```

`conn.String(значение)` возвращает нормальную питоновскую строку. Никакой
проблемы с приведением типов нет — была проблема с именем.

**Как лечить.** Узкий тип исключения, чтобы провал был виден:

```python
def s(self, value):
    try:
        return self.conn.String(value)
    except AttributeError:          # только AttributeError, не Exception
        raise
```

**Вывод важнее самого случая: глобальный контекст двуязычен несимметрично.**
`Метаданные`, `Найти`, `Получить`, `Количество`, `Выполнить`, `Выбрать`,
`УстановитьПараметр` — русские и работают. `String` и `NewObject` — **только
английские**. У реквизита метаданных русское имя есть, но другое:
`ПроверкаЗаполнения`, а не `ЗаполнениеПроверять`. Закономерности нет,
угадывать нельзя — только `GetIDsOfNames`.

Побочный эффект, о котором стоит знать: приём «пробуем русское имя, потом
английское» в PowerShell работает именно из-за этой несимметричности — и ровно
поэтому же скрывает, какое имя настоящее.

## Ложный `catch`

Отдельно, потому что это не грабля платформы, а приём, который кажется
универсальным и не работает ни в одном из двух случаев применения.

Конструкция «попробуем вариант A, а если не вышло — вариант B» для перебора
имён:

```powershell
function Try2 { param($a,$b) try { & $a } catch { & $b } }   # НЕ РАБОТАЕТ
$md = Try2 { $c.Metadata } { $c.Метаданные }
```

**Там, где ошибки нет, он бесполезен.** По грабле 1 чтение свойства точечной
нотацией не бросает исключение — оно возвращает `$null`. Значит `catch` не
срабатывает никогда, вторая ветка не пробуется ни разу, и наружу всегда идёт
результат первой. `$null` едет дальше и падает в другом месте.

**Там, где ошибка есть, он опасен.** По грабле 5 широкий `except Exception`
в Python ловит `AttributeError` от несуществующего имени и возвращает
подставное значение. «Нет такого имени» превращается в правдоподобный мусор,
который проходит все дальнейшие проверки и портит результат молча. Цена в
реальном прогоне: пока подменённое значение возвращало не то, сравнение
`"платежное поручение" in вид.lower()` всегда давало `False`, отсев ложных
находок не работал, и в сводку вернулись **7 ложных тревог из 8**.

Правильно — две вещи вместо `try/catch`:

1. **Явная проверка результата.** Прочитали — проверьте на `$null` / `None`
   прямо здесь, а не через сто строк.
2. **Узкий тип исключения.** `except AttributeError`, а не `except Exception`.
   Если ловите ради ветвления — ловите ровно то, что означает «этого имени нет»,
   и ничего больше.

## Как искать такие грабли

Все пять тихие, поэтому обычная отладка их не показывает: значение выглядит
правдоподобно, а неправильно оно по типу или по содержимому на три часа. Что
работает:

**Держать две независимые реализации и сверять вывод.** Пока проверка живёт
в одном экземпляре, у неё нет эталона: цифра либо есть, либо её нет, и «8 вместо
4» ничем не отличается от правды. Две реализации на разных языках дают разные
грабли, и расхождение в выводе указывает прямо на место. Обе грабли Python
(4 и 5) найдены именно так. Обратная сторона — два источника правды, поэтому
парная реализация имеет смысл как временный режим сверки, а не навсегда.

**Выводить типы при отладке, а не только значения.** `System.Object[]` вместо
`System.__ComObject`, `PSObject` вместо `String`, `<COMObject <unknown>>` вместо
`str` — все три грабли PowerShell и одна питоновская видны в типе и невидимы
в значении. Печать `.GetType().FullName` / `type(x)` рядом с самим значением
стоит одной строки и экономит часы.

**Проверять имена через `GetIDsOfNames`, а не догадкой.** Догадка не отличает
«имени нет» от «имя есть, но вызов не сработал», и в обоих случаях выглядит
одинаково. Тот же принцип шире: имена метаданных — справочников, документов,
перечислений — надо брать из самой конфигурации (список из `Метаданные.*` и
поиск по маске), а не писать литералом по памяти. Ошибка в одной букве даёт
пустую коллекцию, а не исключение.
